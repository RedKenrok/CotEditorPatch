# Patch 4: remote files

`patches/04-remote.patch` adds **editing of files on SSH servers over SFTP**, one by one or from a remote folder window, and makes the app `CotEditor-Remote.app`, which also has file tabs, shell tabs and webpage tabs. The Mac's own OpenSSH client makes the connection and asks the server for its SFTP subsystem. Nothing is installed or run on the server. It is the delta from the exact exported state of [patch 3](03-webpage.md) and does not apply to plain upstream or to upstream with only patches 1, or 1 and 2.

See [the overview](README.md) for how the three patches divide the work. Where the result differs from the plan it was built from, this document says so.

## What users get

1. **File > Open Remote File…** (also in a folder window's **+** menu) asks for a saved connection or a host (an SSH alias), optional user and port, and an absolute path. Recent paths are remembered per connection. **File > Open Remote Folder…** opens a folder on the server in a window of its own, with its tree in the sidebar, where items can be created, renamed, moved and deleted; see [Remote folders](#remote-folders).
2. CotEditor evaluates the SSH configuration, connects, resolves the path, and downloads the file.
3. The file opens in an ordinary editor tab of the folder window, or in a window of its own if file tabs are off or there is no folder window. The tab shows the file name, like any file's tab; the tooltip, the window subtitle and the inspector name `user@host:/path`.
4. **Save** checks the server's file against the version the edits are based on, uploads, verifies, and reports success only when the server has confirmed the result.
5. On failure the document stays open and edited, the edits stay in local recovery, and the alert offers what fits: Retry, Keep Editing, Save a Local Copy, or, for a conflict, Open Remote Version, Save As Remote and (after review) Replace.

Also: **Save As Remote…** (a new path on the same server, never overwriting), **Save a Local Copy…**, **Revert to Remote Version**, **Copy Path** (`user@host:/path`), duplicate as an ordinary local document, and a **Remote File** section in the document inspector (server, path, status, size on the server, temporary files left on the server).

## Build configuration

- The Remote app is built from every patch, so it contains file tabs, terminals and webpages as well, and keeps patch 3's `NSAllowsLocalNetworking`. The Tabs, Terminal and Web apps are built from shorter prefixes and contain no remote code.
- Sources are in `CotEditor/Sources/Remote/`, with names starting with `Remote`. Shared files and tests are edited directly; nothing is behind a compilation condition.
- The only build setting the patch changes is the bundle identifier in `Configurations/CotEditor.xcconfig`, `local.coteditor-tabs.CotEditor-Remote`, so the app does not share preferences, saved windows or recovery records with the Terminal or Web app or a regular CotEditor. Product and module name stay `CotEditor`; `build.sh` copies the app as `CotEditor-Remote-<architecture>.app`.
- The entitlements are patch 2's: no App Sandbox, no iCloud, the hardened-process entitlements kept, library validation disabled only for ad-hoc signing.
- **Why unsandboxed.** Using the user's own OpenSSH setup means running `ssh`, which reads `~/.ssh` and talks to the agent socket; a sandboxed app's child inherits its sandbox. The app also contains terminals.
- No package is added.

## Transport

Three layers, each replaceable in tests:

- `RemoteSSHProcess` launches `/usr/bin/ssh` from its absolute path with an argument array, no shell and no PTY: `-T -a -x -s`, the safety options `BatchMode=yes`, `StrictHostKeyChecking=yes`, `ClearAllForwardings=yes`, `ForwardAgent=no`, `ForwardX11=no`, `ControlMaster=no`, `ControlPath=none`, `PermitLocalCommand=no`, `RemoteCommand=none`, `RequestTTY=no`, `ForkAfterAuthentication=no`, `StdinNull=no`, `Tunnel=no`, `ConnectTimeout=15`, `ServerAliveInterval=15`, `ServerAliveCountMax=2`, then `-l`/`-p` if given, `--`, the host and the constant subsystem `sftp`. `BatchMode` is `no` while CotEditor answers questions (below), and `yes` otherwise. The environment is only `HOME`, `USER`, `LOGNAME`, `SSH_AUTH_SOCK`, `LANG`, a fixed `PATH`, and CotEditor's own askpass program with `SSH_ASKPASS_REQUIRE=force`, or `SSH_ASKPASS_REQUIRE=never` while nobody answers. The write end of the pipe has `F_SETNOSIGPIPE`, so a dead `ssh` gives an error instead of killing the app. `close()` ends the input once any write under way has finished, without waiting for that write, since a write blocks while `ssh` reads nothing; it waits 2 s, terminates, waits 2 s, kills, and waits up to 30 s for Foundation to reap the process, which a process stuck in the kernel may never be. The waits are not cancellable. Each write checks on the queue that closes the input whether it has been closed, so no write can reach a descriptor number that was closed and has since been reused. At most 4 KiB of stderr is kept, sanitized.
- `RemoteSFTPClient` (an actor) and `RemoteSFTPCodec` speak SFTP version 3: `INIT`, `OPEN`, `CLOSE`, `READ`, `WRITE`, `LSTAT`, `FSTAT`, `STAT`, `SETSTAT`, `FSETSTAT`, `OPENDIR`, `READDIR`, `REMOVE`, `REALPATH`, `READLINK`, and `posix-rename@openssh.com` and `fsync@openssh.com` only when advertised with version `1`. The server must answer with version 3 exactly, as a server answers with the client's version or an older one. Requests carry IDs; a reply to an unknown ID, a malformed or oversized packet (limit 257 KiB), the end of the stream, 30 s without progress while requests wait, or a canceled request fails the whole session, and a failed session is never reused: a later request gets `connectionLost`, and only the canceled request itself reports the cancellation. While the session starts, the time without progress does not count while CotEditor's askpass server is asking the user a question, since `ssh` asks for a passphrase or a one-time code before the server can answer; the server does not know which `ssh` asked, so any question counts. The framer keeps a read position and drops the bytes it has taken only now and then, and a request is built behind room for its frame, so a write's data is copied once. A `NAME` reply's names are decoded as bytes, since a folder listing may hold names that are not UTF-8; a path from `REALPATH` or `READLINK` that is not UTF-8 is a protocol error, since it cannot be used as a path. So is a `REALPATH` result that is not absolute and canonical (a `.`, `..` or empty component, or a control character), since it becomes a file's identity and decides what is inside a folder window's root, and a `READLINK` target that is empty or has control characters; relative targets are allowed. `RemotePath.isAncestor` never counts a path with a `.` or `..` component as inside a folder. Attributes whose permissions carry no file type bits describe an item of unknown type, as for missing permissions.
- `RemoteFileTransport` is the protocol that opening and saving use; `RemoteSFTPTransport` implements it. Files are read through one handle with `FSTAT` before and after, in 32 KiB requests, up to 32 in flight, a new one sent for each answer, as far as the size the file had when it was opened plus one request to find its end; a file that grew is read further as its bytes arrive. A short read continues where it ended, and the answers to the requests after it are dropped. An answer with more bytes than asked for is a protocol error. Writes go out the same way, up to 32 in flight. A failed request or a cancellation only stops further requests: every answer and status is awaited, so no request is still on its way afterwards, and a failed read leaves the session usable and its handle closed.

An SFTP status is the server's definite answer. Only a lost reply (`RemoteConnectionError`, a protocol error, or cancellation) leaves an outcome unknown. SSH startup errors are classified from stderr for the message only; no save decision depends on stderr.

**Effective configuration.** Before connecting, `ssh -G` runs with the same options, as a helper (`RemoteHelperProcess`) whose outputs are read while it runs and which is ended after 30 s, or when its task is canceled (terminated, then killed after 2 s), since a `Match exec` command of the configuration may hang or write much; `ssh-keygen` and the key-learning connection run the same way. Connecting evaluates the configuration anyway, and the pool's connector refuses (`destinationChanged`) a configuration that no longer leads to the destination of the connection's key, so an operation checked against one server never runs on another one under its name; and its `hostname`, `user`, `port`, `proxyjump`, `proxycommand`, `userknownhostsfile` and `hashknownhosts` are read. The effective destination, with the route (the `ProxyJump` or `ProxyCommand` value), is part of the file's identity, so a changed route counts as another destination; if it differs at save time, the user is asked, and the file at the new destination is compared with the baseline before anything is written, so a different file there is a conflict.

**Jump hosts.** `ssh` makes a `ProxyJump` connection with a command of its own that leaves out the options given on the command line, so a jump host could ask for a password on a terminal or accept an unknown host key. CotEditor turns the jump hosts into a `ProxyCommand` of its own instead: each jump host gets an `ssh` with the same safety options (`-W [%h]:%p` to the next host), and reaches the jump host before it the same way, with every argument quoted for the shell and the `%` of a nested command doubled once per level, since each `ssh` expands its own. The first jump host is reached as its configuration says, so one that has a `ProxyJump` or `ProxyCommand` of its own is refused (`proxyUnsupported`); naming it in the same `ProxyJump` works. Each jump host is validated as a host is, from `[user@]host[:port]` or `ssh://…`, and an unreadable `ProxyJump` is refused. A `ProxyCommand` is the user's own command, and runs as `ssh` runs it. The connection sheet names the route ("…, through bastion").

**Unknown host keys.** Connections check host keys strictly and never accept a new key on their own. When a connection fails because the key is not known (not when it changed), the pool asks its reviewer (`RemoteHostKeyTrust.review`): a connection of its own (`hostKeyLearningArguments`) writes the key the server offers to a temporary file with `StrictHostKeyChecking=accept-new`, with every method of authentication off, the agent off and batch mode on, so no credential reaches a server that is not trusted yet, and it fails at authentication, by design. `ssh-keygen -l` gives the fingerprint the dialog shows. Only if the user chooses **Trust and Connect** is that exact line added to the first known hosts file of the configuration, hashed if the configuration hashes names; the connection that follows checks strictly again, so it succeeds only if the server still offers the key the user saw. A key that changed is refused with a message that says so, and is never offered for trust. A jump host's key must already be known.

**Questions: passwords, one-time codes and passphrases.** `ssh` asks through `RemoteAskpass.sh`, which the app copies with its command-line tools into `SharedSupport/bin`, where the signature seals it. The program hands the question to `RemoteAskpass` over a Unix socket in a folder of its own (0700, socket 0600), with a random token that only the `ssh` processes CotEditor starts get in their environment; the server also checks that the peer is the same user, and compares the token in constant time. The app asks the user (a secure text field, or Yes and No for a confirmation), and the answer goes back through the socket to the program's output, which `ssh` reads; it never appears in an argument, the environment, a file or a log, and is not stored: the bytes of the reply are cleared once sent, and the string the prompt returns is released as soon as the reply is made, although Swift gives no way to clear it. A question is read on a dispatch queue with a 10-second limit, so a client that connects and sends nothing holds no thread of Swift's cooperative pool and is disconnected; the answer is awaited on a task. Starting and stopping the server are serialized, so two starts cannot both make a socket, and the listener is closed by its dispatch source's cancel handler, once no event handler can still use it. Cancel ends the program with a failure, so `ssh` gives up rather than trying an empty answer. Until the app sets its answerer at launch, and in tests unless a test sets one on a server of its own, nobody answers, and `ssh` runs in batch mode.

**Input validation.** Host and user must not be empty, start with `-`, or contain whitespace, control characters, `%`, `$`, backtick, `;`, `|`, `&`, `<`, `>`, quotes or backslash, at most 255 bytes. The host also must not contain `@` or `/`, which would smuggle a user name or an `ssh://` URI into the destination argument. Ports are 1 to 65535. Paths must be absolute, at most 4096 bytes, without control characters, and are never normalized.

**Connections.** `RemoteConnectionPool` (an actor) keeps one connection per endpoint and destination and runs one operation at a time on it (a FIFO lock), so a save's steps never interleave with another document's. A connection error or protocol error drops the connection; server errors leave it open. An operation that waited for its turn while the one before it dropped the connection connects anew rather than run on the dropped one, whose session would fail it with the other's error (after four attempts it takes the connection it has, so a server that ends every connection at once cannot make it connect without end). Connections close after 2 minutes unused, and any operation is limited to 10 minutes unless the user allows it more time. Generations keep a dropped connection's late results from being taken for the current one's. A connection also has a role: **files** (opening and saving, one operation at a time) or **browsing** (folder listings, up to 4 at once, through the same FIFO lock with room for 4 holders). File operations and listings never share a connection, so a long listing never delays a save, and a listing that fails or is canceled never interrupts one. There is no limit on the number of connections: two per endpoint and destination at most, one of each role.

**Read retries.** An operation that only reads (the downloads and checks of an open, of Revert, and of reconciling an interrupted save) is tried again on a new connection if the connection was lost, at most twice (`RemoteConnectionPool.withReadingConnection`). Server errors, timeouts and failures to connect are not retried. A write is never retried: after a lost connection, whether it arrived is unknown, so the recorded state decides, as described under Saving.

**Starting a session.** The client waits for the server's version reply before it writes its own version request, since a fast server can answer before the write returns. When `ssh` ends before the session starts, the reason is read from its diagnostic output only after that output has ended (for up to 2 seconds), so that a refused host key or login is reported as such rather than as a failure of `ssh` without a reason.

## The document

`RemoteDocument` subclasses `Document`, and its `fileURL` is always `nil`: with a local cache as its URL, AppKit and CotEditor would save to it, watch it, list it in Open Recent and offer it to every local-file command. The overrides:

| With `fileURL == nil`, AppKit would | Instead |
| --- | --- |
| call it "Untitled" | `displayName` is the remote name. |
| open a save panel | `save(withDelegate:…)` runs the save coordinator; `saveAs(_:)` is Save As Remote. |
| write a draft to Autosaved Information | `autosave(…)` writes the recovery record; `autosavesDrafts` is `false`. |
| close an empty untitled document silently | `canClose(…)` asks about every unsent change, including one that empties the file. |
| offer Revert to Saved | disabled; Revert to Remote Version asks, then downloads. |
| restore its own window | its own windows are not restorable; standalone windows come back from the recovery store. |

Reveal in Finder, Share, Rename, Move To, Lock, Unlock, Browse Versions and Revert to Saved are disabled. Duplicate goes through upstream's `duplicate()`, which makes the document from the file type's class, so the result is a plain untitled `Document`.

Downloaded bytes are decoded by upstream's `read(from:ofType:)` through a private temporary file named after the remote file, so the encoding is detected and the syntax chosen from the remote name; the file is removed at once. An unusable remote name (a leading dot, `/`, `:`, control characters, more than 255 bytes) becomes `file` plus its extension.

**Identity.** A remote file is its endpoint, the effective destination and the path `REALPATH` returned, compared byte by byte: Swift's `String` equality treats composed and decomposed characters as equal, but a server's file system generally does not, so `café` spelled either way are two files. The path as asked for is kept too, and resolved again before each save. The profile is not part of the identity, so opening a file through a saved connection and by typing the same values gives the same document. `RemoteDocumentRegistry` finds an open document by identity; `RemoteOpenCoordinator` also joins opens of the same file that are under way, keyed by the path's bytes too, so asking twice opens once and selects the existing tab or window, while the two spellings open two documents. The list of recent paths also tells the spellings apart.

**Symbolic links.** If the path is a link, the user is asked before its target is edited. Saves go to the target, and a link that points elsewhere at save time is a conflict.

**Edited state** means "not confirmed on the server". Writing recovery never clears it. A save takes AppKit's change-count token together with its snapshot and applies it only if that snapshot reaches the server, so edits typed during an upload stay edited.

**Closing** asks Save, Keep Recovery Copy, Discard Changes or Cancel whenever edits are unsent or a save's outcome is unknown. Save must succeed, and edits typed meanwhile are asked about again. Keep Recovery Copy first makes the latest generation durable and fails the close if it cannot. Discard deletes the record only when the document actually closes, so a later Cancel in the same window close or quit keeps it; with an unresolved save, even Discard keeps the record. Tab close, window close, Close All and quit all reach this check through `canClose`.

**Placeholders.** A restored tab whose record is gone becomes a read-only placeholder, "*name* (Not Downloaded)". **Reconnect** (the File menu's Revert item, or the inspector's button) downloads the file and puts the new document in the same tab, at the same place, with the same tab ID. Nothing downloads on its own.

**Environment.** Each document keeps the `RemoteEnvironment` it was created in: connection pool, prompts, recovery folder and recovery timing. The app's commands use `RemoteEnvironment.current`; tests give documents their own.

## Saving

SFTP has no conditional write. The coordinator detects every change it can observe, never overwrites a detected change, and never leaves a half-written file under the real name in the replacing mode, but a writer that changes the file between the last check and the commit cannot be excluded.

`RemoteSaveCoordinator` runs one save or repair per document at a time; later requests queue and take their snapshot when they start. Every save:

1. **Snapshot**, without suspending: `prepareForSaving(for:)`, `encodedContents()`, the text settings, the generation and the change-count token.
2. **Recovery first**: every generation up to now is made durable, then the snapshot and an operation record in state `prepared`. If this fails, nothing is sent. A snapshot over 16 MiB is refused here, after the text is safe in recovery.
3. **Destination** from `ssh -G`, asking if it changed. A new destination under which another document already edits the file is refused before asking, since two documents of one file would each miss the other's edits.
4. **Identity**: `REALPATH` of the requested path must be the recorded path, and `LSTAT` must show a regular file.
5. **Baseline**: the file is read through one handle and hashed (SHA-256). Changed attributes before and after the read, or a different hash, is a conflict. A setuid or setgid file is refused.

**Replacing** (when the server advertises `posix-rename@openssh.com` and reports owner, group and mode): the temporary path `.<name>.cot-<random>` is recorded in the manifest, then created with `CREAT|EXCL` and mode 0600. If creating it is refused, or its owner or group differ from the target's, it is removed and the save becomes a write in place. A target without the owner's write bit is refused. Then: write every chunk and await every status, `fsync@openssh.com` on the open handle if supported, `CLOSE`; `STAT` for the size, read back and hash; apply the target's mode with `SETSTAT` and check it; check the identity and read and hash the target again, also comparing its attributes with the first read; record `committing`; rename; `STAT` for size and mode; record the snapshot as the new baseline; apply the token. A temporary file is removed by its recorded path while the connection works; after a lost connection it is kept and listed in the inspector.

**In place** (the fallback, and repairs): asked once per file and remembered in the record; the consent ends when the record moves to another path or destination, by Save As Remote or a confirmed destination change. Before anything is written in place, the record must say that the operation writes in place and hold the version to restore; if that cannot be recorded, as on a full disk, nothing is written and the save fails as a recovery failure. The target is opened for writing without create or truncate, its handle's attributes are compared with the checked ones, `writingInPlace` is recorded, the snapshot is written from offset 0, the file truncated if shorter, flushed, closed, then its size checked and its bytes read back. From `writingInPlace` on, any failure leaves the outcome unknown. Owner, group, mode and inode stay as they were.

**Save As Remote** creates the new path with `CREAT|EXCL` after recording `creating`, with the permissions of the original for the group and others, so that a private file stays private, and always read and write for the owner, so that the copy can be saved again; setuid, setgid and sticky bits never carry over, and without the original's permissions the copy is 0600. It writes, flushes, closes, verifies, and only then switches the document to the new path. A path that exists is never truncated or removed, even if it holds the same bytes. If the creation's outcome was unknown and the next Save As to the same path finds exactly the snapshot there, the creation is confirmed and the document switches to it, without writing again.

**Nothing to send.** A document that is not edited and whose text encodes to the confirmed version saves without a request, so Save on a clean document does not upload and verify the whole file again.

**Refused**: directories and other non-regular files, setuid and setgid files, files the user cannot write, missing attributes, and snapshots over 16 MiB. The document stays edited, and Save As Remote and Save a Local Copy remain.

**The state decides what a failure means.** After an error, the operation's recorded state, not the kind of error, decides: before `committing`, `writingInPlace` or `creating`, the target is unchanged and the operation is dropped; after it, the outcome is unknown, and the next save checks the server before anything else:

| The server has | Then |
| --- | --- |
| the snapshot | The save is recorded as done, and acknowledged with its token if it is still in memory; after a relaunch the document is clean at once if its text encodes to the snapshot, so the save that reconciled it sends nothing again. |
| the old version | "An earlier save did not reach the server"; Retry is offered, never done by itself. |
| neither | A conflict. After a replacement or a creation, the file there is simply not ours, so the operation is released. After a write in place the file may be mixed, so the operation stays unresolved until a reviewed repair. |
| nothing, another type, or more than 16 MiB | Unresolved; local copies and Save As Remote remain. |

**Conflicts** offer Keep Editing, Open Remote Version (stores the server's bytes as reviewed and opens them read-only beside the document), Save As Remote…, and, only when the server still has exactly the reviewed bytes, Replace. Replace saves against the reviewed version, with all checks. After an interrupted write in place, the same review gates **Retry Upload** (the editor's text in place over the reviewed version) and **Restore Original** (the version from before the interrupted write, which becomes the baseline again while the editor stays edited). A repair that stops before writing brings the unresolved operation back, so the repair can be offered again. The once-per-document consent to writing in place does not cover overwriting a conflict.

**Progress and Cancel.** A save, an open or a Revert that takes longer than a second shows a sheet with its phase (checking the file on the server, uploading, verifying, writing the file on the server, downloading), the bytes transferred, **Cancel**, and **Allow 10 More Minutes**, which moves the operation's time limit later. The operation carries a `RemoteOperationControl` as a task-local value: the transport reports bytes to it and checks for cancellation between windows of requests, when none is outstanding, and the time limit reads its deadline. Cancel follows the recorded state. Before a replacing rename it stops, removes the temporary file and reports the save as canceled, and the document stays edited. From the step that may change the target on (recording `committing`, `writingInPlace` or `creating`), Cancel is disabled and a request is ignored: the operation finishes, or its outcome is reconciled later, and it is never reported as undone. An open or a Revert stops at the next read. A question the operation asks meanwhile, such as the consent to writing in place, takes the sheet's place, and the sheet comes back after it. A window has one sheet, which lists every operation running for it, such as saves of two tabs, each with its own Cancel and more time; Escape cancels only while one is listed. Questions of several operations on one window take turns as sheets rather than becoming application-modal alerts.

**Revert to Remote Version** downloads as an open does, and refuses a version whose attributes changed while it was read, which may mix two versions and so never becomes the baseline. A link that now leads to another file is reported as such.

**Save As Remote during an unresolved write in place** is allowed: the unresolved operation is kept aside in the record, with its data, and the record is not removed while it exists. This goes beyond the plan, which only listed Save As Remote as an option.

## Recovery

`RemoteRecoveryRecord` (an actor) owns all unsent edits of a document, in `~/Library/Application Support/<bundle identifier>/RemoteDocuments/<UUID>/`: folders 0700, files 0600, created with `O_EXCL|O_NOFOLLOW`. AppKit's autosave files are never used.

- **Data files** are immutable and uniquely named (`baseline-`, `text-`, `snapshot-`, `reviewed-` plus a UUID). Each is written, flushed with `F_FULLFSYNC`, and only then referenced by a manifest.
- **The manifest** (a binary property list) names the baseline with its attributes, the current text generation with its encoding, BOM, line ending and syntax, the operation under way with its state, snapshot, expected version and restore copy, the reviewed version, temporary files left on the server, operations kept aside, the in-place consent, and whether the document is open and standalone. It is written to a temporary file, flushed, renamed over the old one, and the folder is flushed. Only then are unreferenced files removed. A crash at any point leaves either manifest with all its data.
- **Generations.** Every change of text or settings, including undo, gets a new generation on the main actor. A generation that is not newer than the stored one is ignored, and an upload's completion changes only its own operation and the baseline, so after "upload A starts, generation B is stored, A completes", B is still unsent against baseline A, also across a restart.
- **Validation.** A manifest must have the right format version and document ID, a valid identity, valid server paths for its operations, their temporary files and the temporary files left on the server, and data file names of the expected form that exist as regular files; data is checked against its digest when read. A damaged record is never deleted.
- **Lock.** A lock file held with `flock` keeps another document or another instance from using the same record. A record that was released or removed refuses every write, so a write that was still waiting when its document closed cannot change a record another document may hold by then; the closed document reports nothing about it. Taking the lock retries for up to half a second, because a process forked at that moment, such as a terminal's shell, holds a copy of the descriptor until it runs its program; listing records does not wait.
- **Scheduling.** Changes are written 1 second after typing pauses, and at least every 5 seconds during continuous typing (`RemoteRecoveryTiming`, injectable). A failed write keeps the previous generation, leaves the document edited, shows "Newer changes not protected" in the inspector, and is reported once until a write succeeds again. For routine autosaves AppKit gets no error, since it would show a second, generic alert; for autosaves that cannot be canceled, as when quitting, it gets the error so that it can stop.
- **Removal.** A record is removed when its document closes clean (outside termination) or after Discard, and never while a save's outcome is unknown or an operation is kept aside. Discard in the Recovered Remote Files window refuses such a record, which may hold the only copy of the server's file as it was before, and asks to open the file to check the server first; a record that cannot be removed stays listed with the error.

**Restoration and launch.** A remote tab is an entry of kind `remoteFile` in patch 1's tab archive: the record's ID, the endpoint, the profile, the requested and resolved paths, and the destination. No credentials and no local path. It reopens offline from the record, in its archived place and with its selection. After windows are restored (or 3 seconds after launch, whichever runs first), unclaimed records are handled: standalone windows that were open come back offline if the system reopens windows; records with unsent text, an unresolved or kept-aside operation, or kept on close are listed in a **Recovered Remote Files** window (Open or Discard); clean records that were closed are removed; clean records that were open but not restored get one more launch (`RemoteLaunchRecovery.decision`). Open shows a record's document where it is if a document holds the record already. A record whose file is open already under another record is not restored, since the registry knows one document per file and a folder window would then rename or delete the file without seeing the second document's changes; the record is kept, and the error says to save or close the file first.

## Remote folders

**File > Open Remote Folder…**, and **Open Remote Folder…** in any folder window's **+** menu, open a folder on the server in a window of its own. **File > Open Recent Remote Folder** reopens one. The window has the folder's tree in the sidebar and the usual tabs; clicking a file opens it as a remote file, through everything described above.

### Opening

- The **Open Remote Folder** window asks for a connection and a folder path, with the folder paths recently opened through that connection (kept apart from file paths). **Open** opens the typed path, or the server's starting folder if none is typed; **Browse…** shows a folder browser instead.
- **Connections** (in both open sheets): a saved connection, a host of the user's SSH configuration, or a host typed in, with optional user and port. The hosts are the aliases of the `Host` lines of `~/.ssh/config` and the files it includes (`RemoteSSHConfigHosts`), without patterns and without names that could not be passed to `ssh`; choosing one leaves the user, port and address to the configuration, which the sheet shows as `ssh -G` evaluates it ("Connects as deploy@example.com, port 22"), without connecting.
- **The browser** starts at the last folder chosen for the connection, and at the server's starting folder (`REALPATH(".")`) if there is none, or, with **Show Starting Folder**, if the last one failed. It has a path field, clickable breadcrumbs, **Up**, the folder's entries, **Show Hidden Files** and **Open Folder**. Files are shown dimmed and cannot be chosen, so the user can recognize a folder by its contents. Double-click or Return enters a folder; an entry without a type, or a link, is resolved first (`REALPATH`, `STAT`, and for a server whose `STAT` gives no type either, a successful `OPENDIR`), and shows **Not a folder** or its error, which entering again retries. **Open Folder** always opens the folder that is shown, never the selected entry.
- **Opening** resolves the path with `REALPATH`, checks with `STAT` that it is a folder, and proves with `OPENDIR` that it can be listed. A failure keeps the window and its fields for correcting them.
- **One window per folder.** A folder window's identity (`RemoteFolderIdentity`) is the endpoint, the effective destination and the canonical path, compared by bytes, as for files; the requested path is kept beside it. `RemoteFolderOpenCoordinator` keeps one window per identity: opening a folder that is open, also through another path or twice at once, brings its window forward. Nested folders may have windows of their own.
- **Open Recent Remote Folder** reopens a recorded connection and path through the same checks. A folder opened with a saved connection that has since been deleted opens the Open Remote Folder window, which asks for a connection; another connection is never substituted. **Clear Menu** empties the list.
- The window's title is the folder's name, its subtitle the location `user@host:/path` while no tab is selected (with a file selected, the subtitle is the file's name, as in a local folder window). The sidebar's header shows the name, the location (with the port, if not 22, in its tooltip), the connection's state, and **Refresh**. It is the sidebar's top accessory, placed by the window right below its title bar where a local sidebar has its pane switcher, without a safe area of its own and with 2 points above its first line.
- **Opening the starting folder** names the folder found, not "wherever a session starts": the window's requested path is that folder's canonical path.

### The window

The window is a `DirectoryDocument` without a file URL, whose [root](01-tabs.md#folders-that-are-not-on-this-mac) is the folder's `RemoteFolderSession`. Patch 1's tabs, members, commands, file tabs preference, close review and tabs of other kinds work unchanged, and no file URL, autosave draft or local path reaches a local command.

### Listing

- `RemoteDirectoryTransport` has the folder operations (`OPENDIR`, `READDIR` and `CLOSE`, with `REALPATH`, `STAT` and `LSTAT`); `RemoteSFTPTransport` implements it, and `listDirectory(at:limits:)` builds a listing from it: `READDIR` until the server's end-of-file status, any other status being a failure. The handle is closed after a complete listing, a server error, a limit or a cancellation.
- **Names.** `.` and `..` are left out. Names that are not UTF-8, or are empty or contain a slash, a NUL or a control character, are left out and counted, and the folder says how many cannot be shown. A name sent twice is kept once. Names are compared by their bytes: `café` composed and decomposed are two entries, as are names that differ only in case.
- **Limits** (`RemoteLimits`): 10,000 entries or 8 MiB of names per listing, counting hidden ones; a `READDIR` answered with no entries also counts, so a server that never ends a listing is stopped. A listing cut short says **Listing incomplete** with the bound that applied; a known child can still be opened with Open Remote File. A window keeps at most 50,000 rows or 32 MiB of names, and lists at most 64 levels below its root; collapsed folders give their rows up first, and an expanded folder that still does not fit says so.
- **Listings are snapshots.** A listing replaces a folder's rows only when it is complete; a failure keeps the previous rows, marked stale, with the error and **Retry**. Rows whose name and type stay the same keep their identity, so their expansion and selection survive; a removed row takes the selection to its closest remaining folder. Refreshing never reloads an editor, clears its edited state or moves its save baseline: each open and save checks the server again.
- **Row animations.** A change of a folder's rows is shown as the rows it removes and inserts (`removeItems` and `insertItems` in one update), so the outline view animates the rows with the space it makes for them; replacing the folder's rows with a reload while it was opening made the rows and the space move apart. A change that reorders rows that stay, or comes while filtering, reloads instead.
- **Settling.** Expanding a folder that is expanded and listed changes nothing and reports nothing, and the sidebar passes only the user's own expansions to the tree. Reloading an expanded row makes the outline view announce its expansion again; before both checks, each such announcement reported a change, which reloaded the row again, and the row kept sliding open.
- **Late replies.** The tree (`RemoteDirectoryTree`), each folder and each connection have generations. Collapsing a folder asks its listings to stop between requests and advances its generation; a reply that arrives after a collapse, a newer listing, a type change or a reconnect is dropped.
- **Types.** An entry's type comes from its attributes. An entry without a type is shown with a question mark and resolved only when it is opened or expanded. A folder that becomes a file or a link loses what was listed below it and its expansion, and a late listing cannot bring them back. A folder whose new listing gives no type keeps its rows only as stale context, lists nothing more until it is confirmed as the same folder, and loses them if it turns out to be another place.
- **Links** are resolved when they are opened or expanded, never just to show a listing. A link to a folder inside the root expands; one that leads to the folder that contains it is a loop and does not expand; one that leads outside the root does not expand either, and opening it opens its target folder in a window of its own. A link to a file opens as a file, which asks about the link as for any remote file. An expanded link is resolved again on refresh and loses its rows if it leads elsewhere. The root is a boundary for browsing, not a security sandbox: the server's permissions decide access.

### Connection, offline and changed locations

- Browsing uses the destination's **browsing connection** in the pool, shared by the destination's folder windows, and closed after the usual 2 minutes unused. Each folder window can therefore cost one more `ssh` connection than its files alone; with an agent that confirms every use, such as a hardware key, opening a folder can ask once more than opening a file.
- **Offline.** A listing that fails because the connection went away takes the window offline: its rows stay, with **Offline** and the reason in the header, and downloaded files stay editable. Opening a file that was never downloaded, or expanding a folder that was never listed, offers **Reconnect**. Saving goes through the document's own connection as always.
- **Reconnect** first checks the window's identity: `ssh -G` gives the destination, and `REALPATH` of the requested path must give the canonical path. Then it lists the root and the expanded folders again. It uploads nothing and reloads no editor.
- **A changed location.** If the path now leads to another folder (such as a link retargeted meanwhile), the window stays offline, with its identity, title, tabs, documents and last-known tree, and its header shows both locations with **Open Changed Location in New Window** and **Cancel**. Accepting resolves the path once more; if it moved again, the new place is shown for review instead, and otherwise it opens in a window of its own, or brings forward the one that has it. Nothing moves from the original window. If the SSH configuration now connects to another server, the user is asked first (**Look Up**), and only then is the folder looked up there; declining leaves the window offline. A missing folder shows **Folder unavailable**, with Reconnect and **Open Another Remote Folder…**.

### Changing items

- **The requests.** `RemoteFolderChanges` makes each change on the files connection (`withFolderEditingConnection`), one operation at a time, waiting behind a save under way, and never tries a request again, since after a lost reply whether it took effect is unknown. A lost reply is reported as such ("it is not known whether the change was made"), and the affected folders are listed again.
- **Creating.** A file is created with `OPEN` and `CREAT | EXCL`, mode `0666`, and a folder with `MKDIR`, mode `0777`; the server narrows both with its umask. The names are upstream's `Untitled`, with the default syntax's extension, and `untitled folder`, numbered as the local file browser numbers them (`Untitled 2.txt`) when taken, up to 100 tries. SFTP version 3 has no status for a name that is taken, so a failed creation counts as one only if `LSTAT` then finds an item there.
- **Renaming and moving** use the plain `RENAME`, never `posix-rename@openssh.com`, which replaces an existing item. OpenSSH's plain rename refuses an existing destination, as the real-server test shows; since another server may replace it, the destination is checked with `LSTAT` first, and a failed rename counts as a taken name if the destination exists afterwards. A rename to a taken name is refused; a move numbers the name, as the local file browser does. A name must be usable as one path component (`RemotePath.isValidComponent`), and is checked before anything is sent.
- **Deleting** asks first, since a server has no Trash. A file or link is removed with `REMOVE`; a link is never followed, since the item's type comes from `LSTAT`. A folder's whole contents are listed first, within the listing limits, 50,000 items and 64 levels, and nothing is deleted if they cannot all be listed or an entry's type stays unknown. Then files and links go, then the folders, deepest first, with `RMDIR`. Cancel on the progress sheet stops between requests, leaving what was not deleted yet. The question says whether a folder's contents go too, and that is what the deletion does: an item confirmed as a file that is a folder on the server by then is not deleted.
- **Open files.** Before a change, every open remote document at or below the item through the same endpoint and destination is found in `RemoteDocumentRegistry`: those whose file is there, and those opened through a path that goes through it, such as through a link. A change is refused before anything is sent if one of them has unsent changes, a save under way or an unresolved operation, or if a file below the item is being opened ("Save or close it first"). Otherwise each document's saves are held (`RemoteSaveCoordinator.withSavesHeld`) until the change ends, so no save can start on the old path, and the check is made again once they are held. After a rename or move, each document's recovery record takes the new path first, then the document (`adoptIdentity`), which registers it under its new identity; its later saves go to the new path. After a deletion, the documents that are still unedited close without review; one edited meanwhile keeps its edits.
- **The tree** shows a change once the server has confirmed it (`RemoteDirectoryTree.insert(_:into:)` and `remove(_:)`): a created item appears at once, a renamed or moved one is removed and inserted at its new place, keeping its expansion, and a deleted one goes. The affected folders are then listed again (`relist(_:)`), which starts over if a listing is under way, so that a reply sent before the change cannot undo it. An item added to a folder that was never listed shows alone, marked stale, until the folder's listing arrives. A row being changed shows a spinner, and does not open, drag or change again until the change is done.
- **Editing a name** makes the row's name field editable only while it is edited, since a click on a file opens it. The name up to its extension is selected, as in the Finder.
- **Uploading.** Items dropped from the Finder are scanned first, without following links (`RemoteUploadItem.scan`): regular files up to the transfer limit and folders are uploaded, at most 1,000 items per drop; links, special files, larger files and names that cannot be used on a server are left out and named afterwards. Each top-level item takes the first free variant of its name in the folder; a folder's contents keep their names, since the folder is new. A file is created exclusively with its local permissions, written, flushed if the server can, and closed. A file that fails while the server still answers is removed again, since this upload created it; after a lost connection it is left, since its state is unknown. The target folder counts as being changed meanwhile.
- **Downloading.** A file dragged to the Finder is a file promise (`RemoteFilePromiseProvider`), which also carries the item's path for moves within the sidebar. The Finder asks for the file once it is dropped; it is read as an open reads a file, within the transfer limit, after a `STAT` shows a regular file, since opening a FIFO would block OpenSSH's server, which handles one request at a time, and the whole session with it; it is written without replacing anything there. Folders are not dragged out.

### Terminals

- **What runs.** A terminal of a remote folder window is its own `/usr/bin/ssh` process in the terminal's local PTY (`RemoteSSHCommand.terminalArguments`): `-tt -a -x`, `RequestTTY=force` and `SessionType=default` (a configuration that asks for no session or a subsystem would never run the command) before the safety options, whose `RequestTTY=no` it overrides since the first value wins, the jump hosts as for SFTP, `--`, the host, and the command. The environment is the one of SFTP connections, with CotEditor's askpass program while it answers questions, and `TERM=xterm-256color`. The local working directory is the home folder; a remote path never becomes a local one. Each terminal is a connection of its own, apart from the pool, so a terminal never delays or ends a listing or a save, nor they it.
- **Starting in the folder.** `ssh` joins its command into one string, which the server runs with the account's login shell, whose kind CotEditor cannot know. The command is `exec /bin/sh -c '<script>' sh <path in hexadecimal>` (`RemoteTerminalCommand`). The script is a constant without backslash, single quote or `!`, so sh, bash, zsh, ksh, dash, fish, csh and tcsh all pass it to `/bin/sh` unchanged; the path is lower-case hexadecimal digits, which no shell treats specially. The script decodes the digits with `awk` in the C locale, enters the folder with `cd --`, and runs `exec "$SHELL" -l`. If the folder cannot be entered, it says so and exits with status 97, and no shell starts anywhere else. No path byte passes through a shell's parser, and nothing is typed into a shell.
- **Before each terminal**, the window's destination is evaluated again through the pool; if the SSH configuration now leads elsewhere, or the window's folder is unavailable or changed, no terminal starts, and the window's Reconnect reviews the change.
- **Ending.** A session that ends with status 0 closes its tab, as a local terminal's does. Any other status, such as `ssh`'s 255 for a refused or lost connection, keeps the tab with its output and a bar with **Start New Session** and **Close Tab**, since the output usually says why. It never reconnects by itself or replays input.
- **Closing and quitting** use patch 2's running-terminal consent and teardown, which ends the `ssh` process; detached jobs on the server are not promised to stop.
- **Not restored.** A remote terminal's tab is not archived: after a relaunch it is gone, as its process is.

### Restoring and closing

- AppKit does not restore a window whose document has no file, so each folder window keeps a record of its own, `~/Library/Application Support/<bundle identifier>/RemoteFolders/<window ID>.plist` (`RemoteFolderArchive`): 0700 folder, 0600 file, written to a new file, flushed and renamed over the old one, on one serial queue, so an older version never replaces a newer one. It holds the format version, the window ID, the folder identity, the tabs (patch 1's tab archive, whose `remoteFile` entries name the documents' recovery records), the hidden-files setting, the window frame, and a snapshot of the loaded rows within the window's limits. No credentials, handles or file contents.
- **With file tabs off**, the record holds the window's member documents, and the one that was showing shows again: patch 1's `restoreTabs(fromArchive:)` restores a root's member documents without tabs then.
- The record is written once changes of the tabs, the tree or the window's frame have settled, and only if it changed: moving the window, resizing it and the automatic refresh ask for it many times, and an unchanged refresh writes nothing. Routine records are flushed with `fsync`; the last one before the app exits also waits for the drive's own cache (`F_FULLFSYNC`). The record is removed when the window closes, except while the app quits. At launch, before the recovery of standalone documents, the records' windows reopen **offline**, making no request: the sidebar shows the snapshot, labeled **Offline, listing not refreshed**, and the tabs come back from their recovery records, which claims those records. Every value of a record is validated when read, and an invalid record is skipped, not deleted. With the system's window restoration off, the records are removed, and unsent edits are offered in the Recovered Remote Files window as for any remote file.
- **Closing** goes through patch 1's close review and the remote close review of each document. A file whose open was past the point of no return when the window closed, such as at the question about a large file, is closed as soon as its open ends, so that it does not stay registered, holding its record, with no window. A canceled close keeps the tree, the documents and the record. Quitting uses AppKit's review, window by window; a window closed before a later one cancels keeps its record, so it reopens at the next launch.

### Where it differs from the plan

The plan for remote folders is implemented, and this section replaces it. The result differs from it here:

- **The container** is a `DirectoryDocument` without a file URL with a root (patch 1's `DirectoryRoot`), rather than a component extracted from it. The spike's questions were answered by building it: tabs off and on, Move to New Window, inspector routing, the disabled terminal commands and offline restoration work through the root, as the tests show.
- **The empty editor** shows nothing, as in a local folder window, rather than "Select a file to open it". The window title has no remote badge; the sidebar's header shows the network symbol.
- **The folder browser** is a window of its own rather than a sheet, since the folder opens in a new window anyway.
- **Copy Remote Location** copies `user@host:/path`; the port appears only in the tooltip.
- **Sidebar width** is shared by every folder window, as for local ones, rather than kept per window.

Terminals in remote folders are implemented, and this document replaces their plan. The result differs from it here:

- **The folder** is the window's root; **Open Shell Here** for a folder of the tree is left out.
- **No badge**: the shell's prompt, which usually names the user and host, tells a remote terminal from a local one; the tooltip names the location.
- **Not restored**, rather than coming back as a placeholder, and **no limit** on terminals per server.
- **The destination is checked when the terminal opens**; Start New Session reuses the arguments made then.
- **Shells tested**: the command runs in `/bin/sh`, bash, zsh, dash, ksh, csh and tcsh on this Mac with hostile folder names; fish is not installed, and the fixture's shell server runs `/bin/sh`.

Changing items is implemented as its plan described, except:

- **Rename** is in the context menu, rather than started by clicking a selected row's name as in the local file browser, since a click on a file opens it.
- **Duplicate**, which the local file browser has, is left out, as the plan said: SFTP version 3 has no copy request.
- **One row at a time**: the sidebar selects one row, so each command changes one item.

## Open questions from the plan

- **Phase 0: does a `fileURL == nil` subclass of the `@Observable` `Document` work?** Yes. Observation fires on the subclass (`observationWorksOnTheSubclass`), AppKit writes no draft and never gets an autosave URL (`theDocumentNeverHasAFileOrAnAutosaveDraft`), `duplicate()` returns a plain `Document`, and tab close, window close and Close All reach the remote close review. Two findings: `Document` needed one private method marked `final` to link, and a document's own window must not be restorable.
- **Phase 0: which patch 1 hooks were needed?** The four expected ones, adjusted: `adoptMember`, the archive order with foreign entries and `arrange(by:)`, and presentation properties. The archive hook became an overridable `tabArchiveRepresentation` on `DataDocument` plus `restoreForeignTabs`, rather than a registry.
- **Phase 4: does an unprivileged `sshd` run on macOS?** Yes, on macOS 27 with OpenSSH 10.3p1, with `UsePAM no`. `sshd` and `ssh` reject key paths with spaces even when quoted, so the fixture's configurations go through a link in the temporary folder. No container is needed.
- **Does AppKit run the remote close review at quit?** No. With CotEditor's autosave in place, AppKit's review of unsaved documents autosaves a remote document instead of asking, which writes its edits to the recovery record, and lets the app quit; the record is kept for restoration (`quittingAsksAboutRunningTerminalsBeforeEditedRemoteFiles`). The edits come back after a relaunch, in their tab, standalone, or in the Recovered Remote Files window. Canceling patch 2's terminal consent ends the quit before any document is reviewed or autosaved.
- **How long does a 16 MiB save take on a slow link?** It was measured by hand on a throttled link, and the limits stay as they are. A replacing save moves the file over the link four times (the check, the upload, the read-back and the final check) and a write in place three times, so at 1 MB/s a 16 MiB replacing save needs about a minute, at 200 kB/s about five and a half, and at 100 kB/s about eleven, beyond the 10-minute limit, which Allow 10 More Minutes can extend. The 16 MiB cap stays: raising it would need a cheaper way to check a large file than reading it whole.

## Known limitations

- **Answers to questions are not kept**, so each new connection asks again; a folder window and its files use two connections. A jump host's unknown key cannot be trusted from CotEditor, and a first jump host must not have a jump host of its own.
- **Remote folders** do not copy items on the server or drag folders to the Finder, upload files over 16 MiB or links. They poll rather than watch, every 30 seconds while visible. The filter's search stops at nine tenths of the window's limits. Deleting is permanent. Between the check of a destination and a rename, another client could create an item there; OpenSSH still refuses the rename, and a server that replaces it could lose that item.
- **Terminals** start in the folder's root and are not restored. A server whose SFTP shows a different view of its files than its shell, such as with `ChrootDirectory`, can start the shell in another folder of the same path, which SFTP cannot detect; a path the shell does not have fails visibly. The account's login shell must accept `-c` and run `/bin/sh`.
- **Listings** read at most 10,000 entries or 8 MiB of names per folder, and a window keeps at most 50,000 rows.
- **The race SFTP cannot close.** A writer that changes the file between the last check and the commit is not detected.
- **Cancel only before the target can change.** Once a rename, a write in place or a creation has started, the operation cannot be canceled; the 30-second limit without progress still applies.
- **Cost of a save.** A replacing save transfers the file four times, an in-place save three times.
- **Replacing** does not keep ACLs, extended attributes or hard links; writing in place does. Paths must be UTF-8.
- **Strings** are English only.
- **Not planned:** a three-way merge view for conflicts (the conflict review stays the way to resolve one), privileged saves and `sudo`, opening files whose paths are not valid UTF-8, and keeping ACLs, extended attributes and hard links in the replacing save mode (writing in place keeps them).
